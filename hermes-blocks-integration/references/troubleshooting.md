# Troubleshooting — symptom → cause → fix

Every row below was hit for real while building the two-agent calendar demo.

| Symptom | Cause | Fix |
|---|---|---|
| RPC error: `Agent declares io.inputs; every requestPart must include a partId` | `textPart(text)` called without the partId second argument (defaults to `"text"`, which doesn't match the card's input id) | `textPart(JSON.stringify(payload), 'request')` — the partId must equal the target card's `io.inputs[0].id` |
| `Request not found or already processed` on approve, but the request is visibly pending | Pending requests kept in an in-memory `Map`; Blocks ran the approve on a fresh handler instance | Persist to disk (`pending_approvals.json`), load fresh per call — see the handler template |
| Same error, but a disk store IS in use | Writer and reader resolve different store paths (host path vs `/opt/data/...` container path, or differing `DATA_DIR`) | Set `PENDING_STORE_PATH` explicitly and verify both processes print the same resolved path |
| Requester never receives the approval/rejection notification; no errors anywhere | Outbound `sendMessage` from inside the handler was fire-and-forget; task teardown killed it mid-flight | `await` every outbound call (Blocks notify, Telegram send) before the handler returns |
| `ReferenceError: require is not defined` in a standalone script | `@blocks-network/sdk` is ESM-only | Use `.mjs` + `import`; for cwd-independent resolution use the `pathToFileURL(path.join(__dir, 'node_modules/...'))` pattern from `runbook.template.mjs` |
| `Cannot find module '@blocks-network/sdk'` from cron/CI but not interactively | Script executed from the wrong cwd; bare-specifier resolution fails | Same fix as above — resolve the SDK relative to the script's own directory, or `cd` to the project dir first |
| `[RPC] Fingerprint required for anonymous tasks` | No Blocks credentials on this machine/user | Owner logs in — browser relay or API-key stdin (see the Login paths in SKILL.md); always with `--write-env --dir <project>` |
| Browser OAuth never completes; browser lands on a dead `http://127.0.0.1:8787/callback?...` page | `blocks login` runs inside a container; its callback listener binds to the container's localhost, unreachable from the host browser | Relay it: owner pastes the full callback URL to the agent, which runs `curl -s "<url>"` INSIDE the container while the login process is still waiting — login then completes normally. (Headless alternative: `--api-key-stdin`.) |
| `blocks run` exits with `BLOCKS_API_KEY is required` although `blocks whoami` works | The runner reads the key from the project `.env`, not the CLI profile; login ran without `--write-env --dir <project>` (non-TTY logins silently skip the `.env` prompt) | Re-run login with `--write-env --dir <project>`, or copy the key into `.env` manually; verify with `grep BLOCKS_API_KEY=bk_ .env` |
| Cross-org call fails with an auth-looking error although both agents are registered and running | Private agents are invite-only; the invite was never sent or never accepted | `blocks invite send <agent> --email <peer>` on one side, `blocks invite accept <token>` on the other, both directions for symmetric setups; check `blocks invite grants <agent>` |
| Telegram sends return 401 | Bot token revoked/rotated — typically a stale token hardcoded as a code default | Tokens from env ONLY, no literal defaults; reissue via BotFather and update `.env` |
| Notification lands in the wrong person's chat on a fresh deploy | A person-specific `TELEGRAM_CHAT_ID` default left in code | No person defaults — require the env var; skip-and-log when unset |
| Second consumer of the same bot gets HTTP 409 `Conflict` on `getUpdates` | One bot allows one update consumer; the gateway already owns it | Route button taps through the gateway (label-as-command reply keyboard) or give the bridge its own dedicated bot token |
| Meeting booked with no attendees, or with a guessed person | Request carried a display name (`"requester": "John"`) instead of an email, and the handler guessed or defaulted | Resolve identity from request fields → `callerClaims`/`ownerId` → otherwise REFUSE with an instructive error (`resolveRequesterEmail`) |
| The same meeting appears twice (once per calendar) | Requester side created its own copy on `notify_approval` | `notify_approval` is notify-only; the ONE event lives on the approver's calendar with the requester as invited guest (`sendUpdates: 'all'`) |
| Approver's event never shows on the requester's Google Calendar | Google only auto-adds invitations if the invitee accepted OR has "add invitations to my calendar" set to auto — and the setting only affects NEW invites | Invitee accepts the email invite, or enables the auto-add setting and re-sends a fresh invite |
| Scheduled slot lands on a weekend or at 3am for one party | Slot search ignored per-person timezones/working hours | Compute the intersection in BOTH owners' timezones with weekday+working-hours guards; widen the working window when zones barely overlap (e.g. Europe↔US-West needs ~8:00–21:00) |
| Handler killed before finishing a slow flow | `runtime.maxRunningTimeSec` smaller than the work (including awaited outbound `waitForTerminal` timeouts) | Raise it in the agent card; budget: domain work + every awaited timeout |
| Agent behaves as if old conversation state persists after a "reset" | Gateway keeps sessions in memory and re-persists them after a DB prune | Prune sessions AND restart the gateway process |
